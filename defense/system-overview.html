Disease Detection System (DDS)

Forensic Mortality Surveillance & Outbreak Early-Warning Platform — System Overview · MOHCC Zimbabwe

1. What the system is

DDS is a real-time forensic mortality surveillance platform. When a death occurs, the information about that death exists immediately — but traditionally it takes days or weeks to become intelligence for district and national epidemiologists. DDS closes that gap: it captures death notifications at the facility, verifies causes of death through autopsy and medical certification, and continuously scans the data — plus pre-mortality feeds — for outbreak patterns, pushing alerts to public health officials within minutes.

Three questions the system answers:
① How many deaths are coming? (forecasting)   ② Is something abnormal happening right now? (five-pass detection)   ③ What is killing people? (cause-of-death analytics)

3. The case lifecycle

  1. Intake — a medical officer enters a death notification (ICD-10 coded at capture), web or mobile (including offline, syncing later via the encrypted queue).
  2. Review — status flow is governed by case-workflow.ts: pending_review → under_review → certified/finalized or rejected, each transition via a dedicated action endpoint (/certify, /reject, /autopsy, /assign).
  3. Verification — natural deaths are certified by a medical officer (HMAC-signed certificate); medico-legal deaths go to a pathologist (autopsy report, tele-pathology images, digital signature).
  4. Detection — every notification triggers the coalesced outbreak engine; a scheduled sweep also runs every 8 minutes.
  5. Response — alerts push to the bell (websocket), email when SMTP is configured, and appear on Alerts / Map / Analytics pages. Signals can escalate into case investigations; playbooks guide response.

4. The five-pass detection engine

detectOutbreaks() in server/src/lib/outbreak.ts runs on every notification intake (coalesced) and every 8 minutes. Each pass is independent; alerts dedupe per district+category.

  1. Stale-alert expiry — outbreak/early-warning alerts older than ALERT_AUTO_RESOLVE_HOURS (336h) auto-resolve so a second wave in the same district re-alerts. MPDSR alerts never auto-resolve.
  2. Threshold clusters — ≥ OUTBREAK_THRESHOLD (8) deaths in a district+category inside OUTBREAK_WINDOW_HOURS. Window uses GREATEST(date_of_death, created_at) so late data entry can't hide a cluster. Cause precedence: autopsy → medical certification → preliminary ICD.
  3. Low-volume early warning — a notifiable disease reaching 2 cases in the window, or a true one-sided Poisson CUSUM flag on the 14-day series, raises an amber early_warning.
  4. Community-signal pass — health_signals (health workers, police, media) + community_reports (public USSD/WhatsApp) pool per district over 72h; ≥3 weighted reports — or one critical — alerts before any death is notified.
  5. Morbidity (syndromic) pass — morbidity_reports: aggregate facility/lab case counts via POST /api/morbidity or FHIR (/api/fhir/Observation, /fhir/Bundle). ≥10 pooled cases per district+category in 168h fires an early warning — true pre-mortality detection.

MPDSR is separate: any maternal/perinatal notification instant-alerts at risk 85.

7. Mobile app — offline-first field capture

  • Offline queue: mutations enqueue as ops (coalescing last-write-wins), apply optimistically, replay through POST /offline/sync or canonical REST paths; outcomes SYNCED/CONFLICT/REJECTED. Encrypted Hive boxes (AES-256) hold the queue, case cache, drafts, and read cache.
  • Biometric sign-in: works online (token re-validated) and offline (14-day window) — MainActivity stays a FlutterFragmentActivity for local_auth.
  • Server discovery: ServerResolver chain — saved override → dart-defines → last-good → platform default — plus UDP-40401 beacon listen + /24 subnet scan + Firebase/GitHub pointers. The laptop's IP is never hardcoded: the beacon re-reads interfaces every 3s, and the app self-heals on network change. The ngrok domain works on any network including cellular/hotspot.
  • Background sync: workmanager task flushes the queue every 15 min when connected.
